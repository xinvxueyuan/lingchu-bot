Cut a Lingchu Bot release by preparing the version on `main` and triggering `release.yml` manually with a `bump` input. There are no `releases/<bump>` branches to push — `task release:publish BUMP=...` runs `gh workflow run release.yml -f bump=...` instead. `release.yml` runs the same `ci:version:bump` → `ci:version:precheck` → `ci:version:write-config` → `ci:version:postcheck` chain that `ci-builds.yml::versioned-build` uses for the daily development build, so a single piece of PEP 440 logic governs every version transition.

## Bump inputs

The `bump` input encodes the **bump intent**, not the literal version. The workflow derives the version from the latest git tag via `uv version --bump`:

| `bump` | `BUMP_LEVEL` | `BUMP_PRERELEASE` | Resulting version |
| --- | --- | --- | --- |
| `major` | `major` | `dev` | `next major + .dev1` |
| `minor` | `minor` | `dev` | `next minor + .dev1` |
| `patch` | `patch` | `dev` | `next patch + .dev1` |
| `stable` | `patch` | `stable` | `next patch` (no pre-release) |
| `alpha` | `patch` | `alpha` | `next patch + a1` |
| `beta` | `patch` | `beta` | `next patch + b1` |
| `rc` | `patch` | `rc` | `next patch + rc1` |

Literal version strings are never accepted as inputs. The workflow `case` rejects them with a clear error.

## Local release flow

<Steps>

1. ### Switch to a fresh main

   ```bash
   git switch main
   git pull --ff-only
   ```

2. ### Run `task release:prepare`

   ```bash
   task release:prepare BUMP=stable
   ```

   The task:

   - Validates `BUMP` against the seven allowed values.
   - Calls `task ci:version:bump BUMP_LEVEL=patch BUMP_PRERELEASE=stable DRY_RUN=true` to compute the next version without mutating `pyproject.toml`.
   - Runs `uv version` to write the version into `pyproject.toml`, then `task ci:version:write-config` to write it into `core/config.py` and `package.json`.
   - Runs `task release:verify-version` to confirm `pyproject.toml` / `package.json` / `core/config.py` agree.
   - Scaffolds `.github/releases/<computed_version>.md` if it does not exist.

   It works on the current branch (`main`) — it does **not** create or switch to a `releases/<bump>` branch.

3. ### Edit the release notes

   Open `.github/releases/<version>.md` (the path was printed by `release:prepare`). Add Highlights, breaking changes, and migration notes.

4. ### Update the changelog and commit

   Add a `## [<version>] - YYYY-MM-DD` section to `CHANGELOG.md` and update the compare links at the bottom, then commit:

   ```bash
   git add .github/releases/<version>.md CHANGELOG.md pyproject.toml package.json core/config.py
   git commit -m "🔧 chore(release): release <version>"
   git push origin main
   ```

5. ### Trigger the release manually

   ```bash
   task release:publish BUMP=stable
   ```

   This runs `gh workflow run release.yml -f bump=stable`, dispatching `release.yml` against the pushed `main` commit.

</Steps>

<Aside type="tip" title="Editing the notes after prepare">

If you only need to re-scaffold the notes file (e.g., after computing the version), run `task release:notes BUMP=stable`. It calls `ci:version:bump DRY_RUN=true` and creates the file if it is missing.

</Aside>

## What the release workflow does

`release.yml` runs five jobs in sequence:

| Job | Responsibility |
| --- | --- |
| `validate` | Derive `BUMP_LEVEL` / `BUMP_PRERELEASE` from the `bump` dispatch input; run `ci:version:bump` → `precheck` → `write-config` → `postcheck`; locate `.github/releases/<version>.md`; expose the computed version to downstream jobs. |
| `build` | Sync the computed version to the dispatch branch if drift is detected (so the tag and source files stay in sync); run `task ci:build`; upload the wheel + sdist. |
| `publish-pypi` | Attest SLSA Build L3 provenance; publish to PyPI via Trusted Publishing / OIDC. |
| `publish-image` | Build and push the Docker image to GHCR with the `latest` tag (stable only) plus `${version}` and `${version%.*}`. |
| `github-release` | Create the `v<version>` git tag on the dispatch commit; create the GitHub Release with the dist artifacts and the body from `.github/releases/<version>.md`. |

The `validate` and `build` jobs both invoke the same `ci:version:bump` task that `versioned-build` runs on the daily schedule, so the source-of-truth for the version lives in one place.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `Invalid release branch / input: <name>` | The `bump` input is not one of the seven bump names. | Use `major`, `minor`, `patch`, `stable`, `alpha`, `beta`, or `rc`. |
| `Missing release notes: .github/releases/<version>.md` | The notes file was not committed before triggering. | Run `task release:notes BUMP=<bump>` to scaffold it, then commit and push before re-triggering. |
| `Tag v<version> already exists on origin` | The tag is already published; `ci:version:tag-only` skips recreation. | Verify the tag matches the commit SHA; if a re-publish is needed, delete the tag on origin and re-run the workflow. |
| CI version drift after `release:prepare` | The developer's local bump produced a different version than CI. | The `build` job's `Sync version files to dispatch branch` step commits the CI-computed version onto the dispatch branch. Verify the resulting commit and tag. |
