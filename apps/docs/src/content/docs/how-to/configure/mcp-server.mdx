Expose Lingchu Bot's messages and bots to external agents through an OAuth-protected MCP v1 resource server on the existing NoneBot ASGI app. The server is disabled by default and never acts as an authorization server or exposes arbitrary adapter APIs.

## Prerequisites

- An OAuth authorization server issuing RS256 or ES256 JWTs with a published JWKS endpoint.
- A reverse proxy terminating public TLS and forwarding only the configured route to the bot.
- An environment variable holding at least 32 UTF-8 bytes for cursor encryption.

## Enable the server

First startup creates `mcp-server.toml` in the plugin configuration directory. Open it and set `enabled = true` only after every security field is ready:

```toml title="mcp-server.toml"
enabled = true
route = "/mcp"
issuer = "https://id.example.com/"
audience = "https://bot.example.com/mcp"
jwks_url = "https://id.example.com/.well-known/jwks.json"
identity_kind = "subject"
cursor_secret_env = "LINGCHU_MCP_CURSOR_SECRET"
read_rate_per_minute = 120
send_rate_per_minute = 20
conversation_send_rate_per_minute = 6
principal_concurrency = 8
conversation_write_concurrency = 2
max_page_size = 200
```

<Aside type="caution" title="Keep secrets out of TOML">

`cursor_secret_env` holds the **name** of an environment variable, not the secret itself. Set `LINGCHU_MCP_CURSOR_SECRET` in the environment to a value of at least 32 UTF-8 bytes. Restart the bot after editing the file. An enabled server fails closed when required settings are absent.

</Aside>

## Authorize principals and grants

Each principal and resource grant is committed as one transaction through the CLI from the repository root:

```bash
uv run python scripts/mcp_admin.py principal-create \
  --principal-id deploy-agent --issuer https://id.example.com/ \
  --identity-kind subject --identity-value oauth-subject-123 \
  --display-name "Deployment agent"

uv run python scripts/mcp_admin.py grant-create \
  --grant-id deploy-agent-group-100 --principal-id deploy-agent \
  --platform qq --adapter '~onebot.v11' --protocol default \
  --bot-id 123456789 --conversation-type group \
  --conversation-id 100000001
```

Other administration commands are `principal-enable`, `principal-disable`, `grant-revoke`, and `grant-list`. Identifiers are exact and wildcards are rejected.

## How JWT validation works

JWTs must pass RS256 or ES256 verification through the configured HTTPS JWKS endpoint. Required claims:

| Claim | Requirement |
| --- | --- |
| `iss` | Exact match with `issuer` |
| `aud` | Match with `audience` |
| `exp` | In the future |
| `client_id` | Non-empty |
| `scope` | Present |
| `nbf` | Optional; cannot be in the future |

When `identity_kind = "subject"`, the `sub` claim is required. When `identity_kind = "client_id"`, that claim is mapped instead.

Scopes are `bots:list`, `messages:read`, and `messages:send`. Scopes alone grant no resource access — an exact Resource Grant is also required for every message operation.

## Available tools and resources

| Kind | Identifier |
| --- | --- |
| Tool | `bots.list` |
| Tool | `messages.list_recent` |
| Tool | `messages.send` |
| Resource | `lingchu://server/info` |
| Resource | `lingchu://bots/{platform_id}/{adapter_id}/{protocol_id}/{bot_id}` |

Reads require durable pre-read audit. Sends require durable pre-send audit, an immediate authorization recheck, and a post-result audit. Timeouts that may have delivered return `uncertain`. Ordered text and public HTTPS images are supported; unsafe download destinations are rejected.
