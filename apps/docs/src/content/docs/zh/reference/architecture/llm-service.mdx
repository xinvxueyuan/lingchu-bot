# LLM 服务

Lingchu Bot 内置一个托管 LLM 运行时，持有 Pydantic AI Agent、将 Agent 响应归一化为稳定的值对象，并将凭据与控制面参数与调用方隔离。该运行时是可选的：当其依赖或配置不可用时，非 AI 机器人服务仍可正常启动。

## 架构

LLM 服务位于 `services/llm/` 下，按职责拆分为多个模块。

| 模块 | 职责 |
| --- | --- |
| `services/llm/runtime.py` | 托管生命周期、profile 缓存、Pydantic AI `Agent` 缓存、稳定的 `respond` / `stream` 接口、热重载 |
| `services/llm/config.py` | 基于 localstore 的 `llm.toml` 解析 `[pydantic-ai]`、`[mcp]` 与 `[observability]` 段 |
| `services/llm/agent.py` | `MCPAgentRuntime`，基于已配置的 `MCPToolset` 驱动一次 Pydantic AI `Agent` 运行 |
| `services/llm/mcp.py` | `MCPRuntime`，每个已配置的 MCP 服务器持有一个 `pydantic_ai.mcp.MCPToolset` |
| `services/llm/mcp_lifecycle.py` | MCP Agent 运行时的托管生命周期（初始化/重载/关闭） |
| `services/llm/capabilities.py` | 顾问式、基于模型字符串的能力探测，带进程级缓存 |
| `services/llm/security.py` | 有界不可变数据辅助、日志脱敏与控制面键检测 |
| `services/llm/types.py` | 稳定不可变值对象（`LLMProfile`、`LLMResponse`、`LLMEvent`、`LLMUsage`） |
| `services/llm/events.py` | 将提供商原生流事件无损投影为 `LLMEvent` |
| `services/llm/observability.py` | 用于调用可观测性的结构化 `LLMCallRecord` 发射 |

公共包 `services/llm/__init__.py` 重新导出稳定接口，并通过 `__getattr__` 惰性加载运行时较重的符号，因此导入该包永远不会触发 `pydantic_ai` 或提供商 SDK 的导入。

## 配置

LLM 配置从通过 `nonebot_plugin_localstore.get_plugin_config_file()` 解析的
`llm.toml` 加载。AI 功能需要由操作员维护该文件，并声明显式 `[pydantic-ai]` 段。
旧的 `[profiles]`、`[router]` 与 `[eve]` 段会被忽略并以弃用警告提示，便于
操作员逐步迁移。

### Pydantic AI 配置

`[pydantic-ai]` 段由严格的 Pydantic 模型（`PydanticAIConfig` 且 `extra = "forbid"`）校验。

```toml
[pydantic-ai]
model = "openai:gpt-5.2"                 # 必填，正则：^[\w.-]+:[\w./-]+$
api_key_env = "LINGCHU_AI_API_KEY"       # 环境变量名（可选）
base_url = "https://api.openai.com/v1"   # 可选的提供商 base URL
timeout = 60.0                            # 必须大于零
```

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `model` | 必填 | 必须匹配 `^[\w.-]+:[\w./-]+$`；前缀选择 Pydantic AI 提供商（如 `openai:`、`anthropic:`、`google-gla:`、`google-vertex:`） |
| `api_key_env` | `None` | 持有 API Key 的环境变量名；首次调用时延迟解析 |
| `base_url` | `None` | 可选的提供商 base URL，作为 `model_settings["base_url"]` 透传给 Pydantic AI |
| `timeout` | `60.0` | 单次调用超时（秒），作为 `model_settings["timeout"]` 透传 |

`[mcp]` 表配置显式 MCP Agent（参见
[显式审查的 MCP Agent](#显式审查的-mcp-agent)），`[observability]` 表可切换
结构化调用记录。不再有 `[profiles]`、`[router]` 或 `[eve]` 段；部署级 LLM 字段
不再作为兜底来源。

## 稳定接口

运行时在 `LLMRuntime` 上暴露两个稳定操作：

- `respond(input, *, profile=None, **params) -> LLMResponse` — 一次归一化响应
- `stream(input, *, profile=None, **params) -> AsyncIterator[LLMEvent]` — Agent 流的无损投影

两者都会解析 profile、构造 `pydantic_ai.Agent`（按 `(name, generation, api_key 指纹)` 缓存）、
将旧版输入格式转换为 Pydantic AI 用户提示词与可选的 `message_history`、把非控制面
`params` 合并进 `model_settings`，再委托给 `agent.run()` / `agent.run_stream()`。
组装出的 `LLMResponse` 始终携带 `text`、`output`、`usage`、`request_id`、`model`、
`backend`（始终为 `"pydantic_ai"`）以及 Pydantic AI 的 `raw` 结果对象。

`Agent` 构造使用 `defer_model_check=True`，因此提供商与 API Key 校验会延迟到首次
`run` / `run_stream` 调用。这使得运行时可以在部署中引用的环境变量（例如
`OPENAI_API_KEY`）尚未就位前先完成构造。

### 旧版后端访问

`LLMRuntime.openai(name=None)` 与 `LLMRuntime.litellm(name=None)` 作为弃用桩函数保留：
两者始终抛出 `_WrongBackendError`（一种 `LLMConfigurationError`）。OpenAI 与 LiteLLM
后端类已移除。原本需要原生 SDK 句柄的调用方现在要么使用稳定的 `respond` / `stream`
接口，要么自行直接构造 Pydantic AI `Agent`。

## 能力探测

`services/llm/capabilities.py` 通过 `CapabilityRegistry.probe(profile, capability, *, backend)`
暴露顾问式、模型感知的探测。探测返回 `CapabilityResult`，其 `support` 取以下值之一：

- `supported` — 模型字符串前缀已知可通过 Pydantic AI 的提供商集成支持该能力
- `unsupported` — 当前启发式不会返回此值（统一回退为 `unknown`）
- `unknown` — 模型字符串对该能力不具备权威性

仅支持 `"web_search"` 一项能力。探测是纯启发式：模型字符串以 `openai:`、`anthropic:`、
`google-gla:` 或 `google-vertex:` 开头时返回 `supported`，其他前缀返回 `unknown`。
`backend` 参数仅为与旧版调用方（典型如 `contracts.py`）的签名兼容而保留，但会被有意忽略——Pydantic AI Agent 不暴露统一 SDK 探测面。

`unknown` 永远不会阻止调用。结果按 `(profile.model, capability)` 缓存，并在配置重载后
由 `invalidate_capability_cache()` 失效。

## 错误映射

`runtime.py` 中的 `_normalized_error()` 将 Pydantic AI 与底层提供商 SDK 抛出的异常
映射到项目的 `LLMError` 体系。每个被映射的错误都携带 `backend="pydantic_ai"`、
`model`，以及（若可用）`status_code`、`request_id` 与 `retryable` 提示。

| 来源异常 | 映射错误 | 说明 |
| --- | --- | --- |
| `pydantic_ai.exceptions.ModelHTTPError`（状态 401、403） | `LLMAuthenticationError` | 提供商拒绝凭据 |
| `pydantic_ai.exceptions.ModelHTTPError`（状态 429） | `LLMRateLimitError` | `retryable = True` |
| `pydantic_ai.exceptions.ModelHTTPError`（状态 408、504） | `LLMTimeoutError` | `retryable = True` |
| 其他 `ModelHTTPError` | `LLMProviderError` | 携带 `status_code` |
| `asyncio.TimeoutError`、`TimeoutError` | `LLMTimeoutError` | `retryable = True` |
| `ImportError`、`ModuleNotFoundError` | `LLMDependencyError` | 缺少 `pydantic-ai` 或提供商 SDK |
| `ModelAPIError`、`AgentRunError` | `LLMProviderError` | 通用 Agent/模型失败 |
| 类型名包含 `connect` / `connection` 的异常 | `LLMConnectionError` | `retryable = True` |
| 其他任何异常 | `LLMProviderError` | 兜底 |

## 安全

### 控制面键拒绝

`security.py` 中的 `CONTROL_PLANE_KEYS` 是一个冻结键集合，调用方不得通过稳定接口传入。
它覆盖凭据（`api_key`、`access_token`、`azure_ad_token`）、端点（`base_url`、`api_base`、
`azure_endpoint`、`organization`、`project`）、传输（`transport`、`http_client`、`client`）、
回调（`callback`、`callbacks`、`success_callback`、`failure_callback`、`custom_logger`、
`logger_fn`、`loggers`）、头与查询（`headers`、`extra_headers`、`default_headers`、`query`、
`extra_query`、`default_query`）、重试控制（`max_retries`、`retry`、`retries`、`retry_config`、
`retry_policy`、`retry_strategy`、`num_retries`、`allowed_fails`、`fallbacks`、
`context_window_fallbacks`、`content_policy_fallbacks`）以及 `router` / `token`。

当任一 `**params` 键与 `CONTROL_PLANE_KEYS` 相交时，`LLMRuntime.respond()` 与
`LLMRuntime.stream()` 会抛出 `_ControlPlaneParameterError`（一种 `LLMConfigurationError`）。
按调用传入的 `params` 仍可携带提供商接受的模型设置（例如 `temperature`），仅上述
控制面键会被拒绝。

### `LLMRuntime` 不自动执行工具

`LLMRuntime.respond()` 与 `LLMRuntime.stream()` 绝不执行工具调用。稳定接口是无工具的；
工具执行由下文描述的显式 `MCPAgentRuntime` 承担。

## 显式审查的 MCP Agent

MCP 仅通过 `MCPAgentRuntime` 提供；普通 `LLMRuntime.respond()` 与 `stream()` 始终不带
工具。该功能默认禁用，且只在 `llm.toml` 中配置：

```toml
[mcp]
enabled = true
review_profile = "default"
max_tool_rounds = 5

[mcp.servers.local_docs]
transport = "stdio"
command = "uvx"
args = ["example-mcp-server"]

[mcp.servers.remote_docs]
transport = "streamable_http"
url = "https://mcp.example.com/mcp"
headers_env = "LINGCHU_MCP_HEADERS_JSON"
allow_private_network = false
```

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `enabled` | `false` | MCP 发现与执行的总开关 |
| `review_profile` | `"default"` | 保留作旧版审查 profile 名（仅作兼容保留） |
| `max_tool_rounds` | `5` | Agent 最大轮数；取值范围为 1 到 5 |
| `[mcp.servers.<name>]` | `{}` | 由 `MCPRuntime` 消费的 MCP 服务器定义子表 |

每个 `[mcp.servers.<name>]` 条目是一个 `MCPServerDef`：

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `transport` | 必填 | `stdio` 或 `streamable_http` 之一 |
| `command` | `None` | `stdio` 传输必填 |
| `args` | `()` | `stdio` 传输的参数元组 |
| `url` | `None` | `streamable_http` 传输必填 |
| `headers_env` | `None` | 持有 JSON headers 对象的环境变量名（HTTP 传输） |
| `allow_private_network` | `false` | 信息性标志；HTTP 出站策略由下游强制 |

`MCPRuntime` 每个已配置的服务器持有一个 `pydantic_ai.mcp.MCPToolset`，由
`_build_toolset()` 在首次访问时惰性构造。每个 toolset 包装一个
`fastmcp.client.Client`，使用所选的 `StdioTransport` 或 `StreamableHttpTransport`。
系统只暴露 MCP Tools，不支持 Resources、Prompts、Sampling 与旧版 SSE。模型侧名称
统一为 `<server>.<tool>`。

`MCPAgentRuntime.respond()` 将多轮工具调用循环委托给一个配置了已授权 `MCPToolset` 的
`pydantic_ai.Agent`。Pydantic AI 的原生 Agent 循环负责工具执行；旧版项目侧多轮编排、
LLM 审查步骤与确认流程均已移除。因此 `MCPToolCallOutcome` 上的 `decision` 字段始终为
`None`。`MCPAgentRuntime.__init__` 仍保留 `confirmation_manager` 参数，便于旧调用方
继续编译，但不会被使用。

在任何 Agent 运行之前，现有身份组系统通过 `PermissionResolver` 授予适用范围内的最高
MCP 权限。任意非 `None` 权限级别都授予对全部已配置 MCP 服务器的访问；`None` 会抛出
`MCPAgentPermissionError`。如果 Agent 运行本身抛出异常，`MCPAgentRuntime` 会回退到
不带 MCP 上下文的普通 `LLMRuntime.respond()` 调用，调用方仍能收到稳定的 `LLMResponse`。

MCP 元数据与结果始终按有界的不可信数据处理。

### 有界不可变数据

`security.py` 强制使用有界、不可变、JSON-like 的数据：

- `freeze_value()` 将受支持的值深拷贝为 `MappingProxyType` / `tuple` 容器，含 `MAX_NESTING_DEPTH = 8`、`MAX_COLLECTION_ITEMS = 100`、循环检测，并拒绝非字符串映射键。
- `thaw_value()` 将冻结值拷贝回可变 `dict` / `list` 以供 SDK 调用。
- `sanitize_message()` 在返回有界公开异常文本前，剥离控制/分隔符/Bidi 覆写字符，并对 `Bearer`/`Basic` 授权值与凭据类赋值进行脱敏。
- `LLMProfile.__repr__` 永不渲染 `api_key` 的内容。

## 生命周期与热重载

单个托管 `LLMRuntime` 实例由 `runtime.py` 中的 `_managed_state` 持有，并受 `_managed_runtime_lock` 与一个 `_LifecycleCoordinator` 保护，后者在线程与事件循环间串行化生命周期工作。

| 函数 | 用途 |
| --- | --- |
| `get_llm_runtime()` | 返回进程运行时，首次访问时惰性构造 |
| `initialize_llm_runtime()` | 初始化一次，与重载和关闭串行 |
| `reload_llm_runtime()` | 发布一个已校验的候选运行时，再关闭旧运行时 |
| `shutdown_llm_runtime()` | 分离并关闭进程运行时 |
| `reload_mcp_agent_runtime()` | 原子发布已校验的 MCP 配置，并关闭旧 toolset |
| `shutdown_mcp_agent_runtime()` | 关闭 MCP toolset 并分离 MCP Agent 运行时 |

### 热重载语义

`reload_llm_runtime()` 遵循严格的顺序，使失败的重载永远不会破坏运行中的机器人：

1. 获取生命周期协调器票据（与初始化/关闭串行）。
2. 通过 `_build_managed_runtime()` 以 `next_generation = 当前值 + 1` 构建候选运行时。该步调用 `load_llm_runtime_config()` 并构造 `LLMRuntime`，但不会发布，因此配置校验错误在此暴露。
3. 通过交换 `_managed_state.runtime` 并递增 `_managed_state.generation` 来发布候选。
4. 调用 `invalidate_capability_cache()`，使下次探测重新评估新的模型字符串。
5. 通过 `_finish_cleanup_before_cancellation()` 关闭旧运行时，该函数在所拥有的清理完成前保持生命周期串行化，仅在清理完成后才传播取消。

关闭失败会在交换后传播。新 generation 保持已发布状态，因为回滚到一个已部分关闭的运行时不安全。profile 与 Agent 按 `(name, generation, api_key 指纹)` 缓存，因此旧运行时上仍在进行的调用会继续解析各自的 Agent，直到旧运行时被关闭。Agent 本身没有显式 `close()` 方法，因此清理只是清空缓存的 profile 与 Agent 字典。

### 关闭

`shutdown_llm_runtime()` 将 `shutting_down` 置为 `True`，分离运行时，并清空所持有的全部 profile 与 Agent，单个失败不会中断其余清理。一旦关闭开始，`get_llm_runtime()` 会抛出 `_RuntimeClosingError`。

<Aside title="启动时可选">

`start/startup.py` 只解析 localstore 中的 `llm.toml` 路径而不创建文件，并将 `initialize_llm_runtime()` 包裹在 try/except 中，因此配置或 `pydantic-ai` 依赖失败永远不会阻止非 AI 机器人服务启动。

</Aside>
